# 架構決策紀錄

本文件記錄資料模型、匯入、追溯與製程管制的決策。資料表與端點見 [系統設計](DESIGN.md)。

## P1 資料模型

| 編號 | 採用方案 | 理由與影響 |
| --- | --- | --- |
| P1-1 | 原料批與生產批共用 `lot`，以 `lot_type` 區分 | 批號追溯沿同一張表查詢。各類型專屬欄位以 `CHECK` 保證必填及適用性 |
| P1-2 | 有穩定業務代碼的主資料和批號以代碼作主鍵 | 外鍵可直接辨識批號、站點與機台。代碼意義變更時建立新代碼，歷史資料保留原引用 |
| P1-3 | 業務時間以 PostgreSQL `timestamptz` 儲存 | 以同一時間點比較不同來源。來源只有當地時間時，依既定時區 `Asia/Taipei` 解讀 |
| P1-4 | 計數型紀錄的量測點為 NULL，唯一約束使用 `NULLS NOT DISTINCT` | NULL 表示量測點不適用，唯一約束仍阻擋相同的計數型量測 |
| P1-5 | `lot_link` 的上下游都參照 `lot`，關係區分 `consume` 與 `split` | 資料庫可用外鍵保證兩端存在。原料消耗或生產批分批等跨列規則由主資料套用流程驗證 |
| P1-6 | 系統產生的時間使用 `timestamptz DEFAULT now()` | 採資料庫時計產生上傳時間，讀取時依顯示需求轉換時區 |
| P1-7 | 機台使用半開有效期間 `[valid_from, valid_to)` | 補傳以量測當時判斷，落在停用時點的量測已超出有效期間 |
| P1-8 | 站點、檢驗項目及料號使用 `active` | 停用狀態限制後續匯入，歷史紀錄保留原主資料引用 |
| P1-9 | 檢驗紀錄以 `bigint` 流水號識別，另設量測業務鍵唯一約束 | 以單一 ID 引用紀錄，同時防止批號、站點、項目、片號與量測點相同的量測重複寫入 |
| P1-10 | 單位換算後以十進位運算四捨五入至三位小數，再以 `double precision` 儲存 | 同一尺度下比較重傳值與規格值。數值評估依答案清單的容許誤差比較 |
| P1-11 | 記錄標準單位下的量測值，保留來源檔名、SHA-256 與來源列 | 標準單位由檢驗項目定義。核對成功匯入的原文需使用原始檔案；退件的原始值保留於錯誤明細 |
| P1-12 | 初始化主資料時先比對差異，確認後以一筆交易套用 | 可新增及更新顯示欄位。規格或單位等受保護欄位有變更時拒絕整批，缺少的來源列只提示。可用 `--check` 預覽、`--yes` 在自動化環境確認 |
| P1-13 | 整合測試使用 PostgreSQL，每個測試使用外層交易及儲存點 | 測試內的提交只完成儲存點，測試結束後回滾外層交易 |

## P2 檢驗紀錄匯入

| 編號 | 採用方案 | 理由與影響 |
| --- | --- | --- |
| P2-1 | 操作員必填，C40 舊系統 CSV 以 `OP` 欄提供 | 缺少必要欄位或值時退件。站點日報也從來源讀取，機台 CSV 和人工表單由進出站紀錄取得 |
| P2-2 | 兩個表頭對應到同一欄時整份退件 | 避免依欄位位置任選其中一個值 |
| P2-3 | C40 表頭依別名表精確比對 | 表頭必須完全符合已登錄別名，必要欄位無法辨識時退件 |
| P2-4 | 未登錄的額外欄位保留警告 | 可接受不影響對應的附加欄位；必要欄位缺漏或對應衝突仍退件 |
| P2-5 | 掃描整個檔案，每列最多回報一項阻擋錯誤 | 使用者可一次處理多列問題。同列修正後可再驗證下一項 |
| P2-6 | 逐列依必填、格式、主資料參照的順序驗證 | 先回報資料缺漏，再檢查格式與有效性 |
| P2-7 | 同一層依欄位的標準順序回報 | 調換來源檔案的欄位順序，首個錯誤仍符合相同規則。報告保留來源列與欄 |
| P2-8 | C40 量測值使用小數點 | 含逗號的量測值回報 `E_NOT_NUMERIC`。仍可正規化全形字元與頭尾空白 |
| P2-9 | C40 操作員須符合 `OP-[0-9]{4}` 並登錄於模擬名單 | 格式正確但未登錄時回報 `E_REF_NOT_FOUND` |
| P2-10 | 量測業務鍵相同時先比對正規化數值 | 相同數值可略過；不同數值整檔退件並保留原量測。受控的歷史更正另行規劃 |

C40 的標準欄位順序為 `LOTNO → PNL → PT → EQP → ITEM → VAL → UOM → DT → TM → OP`。檔案指紋與量測業務鍵分別處理相同檔案重傳，以及內容相同但檔案位元組不同的情形。

## P5 批號追溯與 Q-time

批號追溯沿 `lot_link` 遞迴查詢，依查詢方向處理上游或下游關係，並以已走訪路徑防止循環。Q-time 以規則指定的上游出站、下游進站時間計算。分批沿用上游等待時保留原始批號，期間彙整以原始批計算一次。

## P6 統計製程管制

- 採用方案 A，查詢期間開頭的觀測值用作基準，預設 20 筆，可改為 5 至 200 筆。這個選擇減少展示時的設定步驟；若要跨查詢重用同一段基準，需保留相同的查詢起點與基準點數。

- 每張圖使用同一項連續量測與同一機台。查詢開頭的量測建立固定基準，後續異常值不會拉動本次查詢的界線。監測時應選擇歷史條件相近、製程穩定的基準期間。
- I 圖中心線為基準平均值，管制界線為平均值 ± 3 × 平均移動全距 / 1.128。MR 圖計算相鄰兩點的絕對差，基準中心為平均移動全距，上限為其 3.267 倍，下限為 0。第一筆量測沒有前一點，移動全距留空。 [NIST 個別值管制圖](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc322.htm) · [NIST 管制圖常數](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc321.htm)
- I 圖超出上下管制界線時標記。連續 8 個監測點在中心線同側時，標記第 8 點，碰到中心線或換側後重新計數。MR 圖在全距超出上限時標記。製程管制界線由資料估算，產品規格上下限則由檢驗項目主資料定義。 [NIST 管制圖判讀](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/contchar.htm)

## P7 共用查詢與 MCP

- REST 和 MCP 共用查詢服務。MCP 使用官方 Python SDK 2.x 和本機 stdio，讓客戶端啟動子程序並以標準輸入輸出傳遞請求。 [官方 Python SDK](https://py.sdk.modelcontextprotocol.io/)
- MCP 查詢使用獨立的 PostgreSQL 唯讀交易，查詢敘述限時 5 秒。稽核另開交易，記錄進入服務的工具和資源呼叫及其結果。工具輸入在 MCP 協定層被拒絕時，尚未進入服務。
- 批號、量測 ID、來源檔案和列號供使用者核對證據。管制查詢僅回傳摘要和有限筆訊號，分組統計回傳一個代表量測 ID。
